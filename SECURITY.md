# Security Policy and Threat Model

## Scope

MetaForge accepts AI-proposed Python source only in the source-level integer-sorting experiment. Candidate source is untrusted, even when generated by a configured model. The descriptor optimizer and the trusted C/Rust backends are separate paths; the latter compile repository-owned source only.

A separate local project-snapshot/PatchSet API now captures allow-listed text-source manifests and applies hash-preconditioned changes only to a new disposable copy. It is not currently connected to an LLM, project build, test runner, or compiler orchestration.

## Security controls

The source-level path applies multiple independent controls:

1. Strict structured model output, no agent tools or handoffs, one turn per proposal, bounded call time, global experiment deadline, and a finite call budget.
2. A conservative AST policy that rejects non-allow-listed imports, wildcard imports, direct dynamic execution and common I/O/reflection calls, dunder attribute access, selected filesystem mutation methods, asynchronous functions, classes, defaults, annotations, and oversized syntax trees.
3. Mandatory rootless-container preflight and a trusted smoke probe before model calls.
4. A SHA-256-pinned local image; the runtime does not pull images during candidate execution.
5. No container network, read-only root filesystem, read-only workspace, non-root UID, all Linux capabilities dropped, no-new-privileges, CPU/memory/swap/PID limits, bounded temporary storage, bounded output, file/process limits, and wall-clock timeout.
6. A trusted in-container wrapper that measures only the candidate call, validates result shape, and rejects incorrect results.
7. A second host-side correctness oracle before a candidate can be selected.
8. Immutable run archives with dataset hashes, source fingerprints, and lineage; replay repeats review and sandbox checks without a model call.

The project PatchSet foundation has a separate set of controls:
- Strict versioned schema, allow-listed source/documentation roots, relative POSIX paths, Unicode normalization, traversal and Windows reserved-name rejection.
- Dependency/build/lock manifests, CI/hidden paths, binary assets, shell/batch scripts, and existing acceptance tests are excluded or protected by policy.
- Per-file, total-patch, snapshot-file-count, and snapshot-byte budgets.
- Replacement/deletion require the exact captured SHA-256; create requires the target to be absent; case-colliding paths are rejected.
- Snapshot capture rejects symlinks and special files in included roots and hashes files while checking for concurrent modification.
- Patch application re-captures the source, copies only the manifest to a temporary sibling directory, checks file hashes while copying, applies changes atomically, validates the staged snapshot, and installs only into a previously absent destination. The source checkout is never changed.
- This API does not run candidate code, build scripts, compilers, or tests.

A local heuristic secret scanner is available for the files in a captured project snapshot. It checks common private-key headers, OpenAI-style keys, GitHub tokens, AWS access-key IDs, Google API keys, Slack tokens, JWT-like values, credential assignments, and credentials embedded in URLs. Reports contain only path, line number, rule identifier, and severity; matched values are never serialized. Every scanned file is re-read and its SHA-256 is checked against the snapshot before inspection.

The scanner is a best-effort filter, not a complete secret detector. It can produce false positives and false negatives, and it only scans files included in the snapshot (not excluded hidden folders, binary assets, environments, caches, or build outputs). A report with no findings means only that this ruleset detected no known patterns in the scanned snapshot. It does not prove the project contains no secrets or authorize sending the project to an external model. Human review and a stronger dedicated secret-scanning/redaction gate remain mandatory before any future model-context integration.

## Explicit non-guarantees

- AST review is not a proof that Python code is safe. Python's dynamic object model makes static allow-lists inherently incomplete.
- A rootless container is a defense-in-depth boundary, not a formal proof against container-runtime, kernel, WSL, hypervisor, or host vulnerabilities.
- CPU and memory limits do not eliminate all denial-of-service risks against the host or container daemon.
- Timing measurements may be noisy and do not establish general performance improvements without representative workloads and controlled repeated trials.
- Current model-generated source support is Python-only and restricted to integer sorting. The structured multilingual PatchSet foundation is not yet connected to agents and does not yet implement repository-wide refactoring.
- The snapshot captures only allow-listed UTF-8 text paths; binary assets and excluded directories are not copied. It does not currently detect hardcoded secrets inside included source files. Do not send project content to a model until a secret-scanning/redaction stage has been implemented and reviewed.
- The patcher validates file operations but does not prove that the resulting copy builds, passes tests, preserves behavior, or is secure. There is no project-level test/build sandbox integration yet.
- The C11 and Rust backends execute trusted repository source; they do not accept generated native programs.

## Operational requirements

- Use a disposable VM or dedicated isolated host for high-risk experiments.
- Keep API keys outside experiment containers and never commit keys, tokens, personal data, or private datasets.
- Treat project snapshots as sensitive local data. Run the local secret scanner and manually review results, but do not treat a clean heuristic scan as proof of absence or as sufficient authorization to transmit project files.
- Keep the sandbox image pinned by digest and update it only through reviewed dependency/image changes.
- Do not disable rootless mode, no-network enforcement, cgroups, read-only mounts, or other sandbox controls to make a failing test pass.
- Treat any sandbox preflight or smoke failure as a hard stop: no model proposal or candidate execution should occur.

## Reporting

Report suspected vulnerabilities privately to the repository owner. Include the affected commit, minimal reproduction, impact, and environment details. Do not publish exploit payloads for an unpatched issue.
